You are a software engineer responsible for implementing and testing the capabilities of AI models on the API change subtype within the Feature & improvement category.
Your task is to provide two separate, complete Python projects that demonstrate a before-and-after migration from an old API to a new API, and to validate the change with automated tests, reproducible environment scripts, and one-click execution.

Evaluation of Claude-Sonnet-4.5, Claude-haiku-4.5, raptor-secondary, oswe-mini-prime, oswe-mini-m21a2s260, oswe-mini-secondary on Feature & improvement – API change

Description
This experiment evaluates AI models’ ability to implement, validate and harden an API change in a production flow. Canonical example: a commerce platform migrates inventory checks from /api/v1/checkStock to a region-aware /api/v2/stock/availability that requires additional params (regionId, warehouseGroup) and may return asynchronous/partial availability fields. The shopping cart service still calls the old API, causing incorrect availability, increased latency and wrong “out of stock” displays during peak promotions. The objective is to (1) reproduce the faulty behavior, (2) implement the updated API call and response handling, (3) add robustness for the new asynchronous fields, and (4) prove correctness and performance with automated tests and comparative metrics.
Key evaluation criteria
• Correctness and compatibility of both pre-change and post-change implementations.
• Proper handling of the new API schema (parameters, response shape, async fields).
• Backward compatibility strategies (graceful fallback, feature flagging, adapter patterns).
• Performance and latency impact (request duration, error rates).
• Robust test coverage for normal, boundary and malformed inputs.
• Reproducible environment and one-click execution producing a comparison report.

Requirements for the AI Model Output
1.	Test Scenario & Description
o	Clearly describe the API change scenario and the specific capability under test: e.g., migrating from /api/v1/checkStock to /api/v2/stock/availability which adds regionId and warehouseGroup and may return availabilityStatus plus delayed syncTimestamp.
o	Specify expected input and output formats (JSON/Python dict). Example input for new API: {"sku":"ABC123","regionId":"ap-sg-1","warehouseGroup":"WG-2"}. Example response: {"sku":"ABC123","available":true,"quantity":12,"availabilityStatus":"confirmed","syncTimestamp":"2025-11-01T12:00:00Z"}.
o	Define acceptance criteria: updated service calls new endpoint with correct parameters, correctly interprets asynchronous fields, falls back or degrades gracefully if the new API returns partial data, and produces identical or improved user-facing behavior vs baseline.
2.	Test Data Generation
o	Generate at least 5 structured test cases (saveable as test_data.json) covering:
• Normal case — new API returns immediate confirmed availability.
• Boundary case — quantity == 0 or exactly the reserve threshold.
• Asynchronous/partial case — response with availabilityStatus: "pending" and later update via syncTimestamp.
• Invalid/malformed inputs — missing regionId, invalid warehouseGroup, non-string SKU.
• High-latency / error case — timeouts, 500 errors, or delayed retries from v2.
o	Include expected outputs for each test (HTTP status, parsed availability, fallback decision) and pass/fail rules.
3.	Reproducible Environment
o	Provide requirements.txt, setup.sh, and optionally a Dockerfile to install dependencies and run both projects (pre-change and post-change).
o	Document environment config (e.g., base URLs, feature-flag toggle, mock server ports) and instructions to start mock upstreams that emulate /api/v1 and /api/v2 behavior.
o	Include guidance to toggle between live vs mock endpoints for integration tests.
4.	Test Code
o	Produce executable Python test code that:
a. Starts mock upstream APIs (v1/v2) with configurable behaviors (latency, partial responses, errors).
b. Deploys and runs the service under test (Project A or B).
c. Sends test requests based on test_data.json.
d. Captures outputs, HTTP responses, internal logs, and timing.
e. Validates parsed results vs expected outputs and reports pass/fail per case.
f. Computes evaluation metrics: accuracy of availability decision, latency percentiles, error/retry rates, and fallback frequency.
o	Tests must be automated and runnable via run_tests.sh.
5.	Execution Scripts
o	Each project must include run_tests.sh that: provisions environment (venv or Docker), starts mocks and service, runs the test suite, collects logs and metrics, and stops components.
o	Provide a root-level run_all.sh that runs Project A tests first, then Project B tests, aggregates results_pre.json and results_post.json, and produces compare_report.md. A single command should execute the full workflow.
6.	Expected Output
o	For each test case produce: expected HTTP status, expected parsed availability decision (e.g., { "available": true, "quantity":12, "note":"confirmed" }), and expected fallback outcomes for errors.
o	Produce machine-readable results files: results_pre.json and results_post.json with per-case assertions, latencies, and error counts.
o	Generate a compare_report.md summarizing: correctness diff, latency comparison (p50/p95), error/retry rates, fallback frequency, and key observations (e.g., cases where v2’s async field required polling and how implemented).
7.	Documentation / Explanation
o	Include README.md explaining how to run each project individually and the full run_all.sh workflow.
o	For every test case, explain what it verifies (parameter mapping, async handling, fallback).
o	Highlight pitfalls (schema drift, missing parameters, inconsistent timestamp formats, eventual consistency issues) and suggested mitigations (strict validation, idempotent retries, circuit breakers, observability).
o	Enumerate limitations of the tests (mock fidelity vs production, network conditions not fully simulated) and recommended production rollout steps (canary, feature flags, gradual traffic shift).
